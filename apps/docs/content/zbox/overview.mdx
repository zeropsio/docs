Zerops Box runs **sandboxes for AI agents** on Zerops. A sandbox is a small, isolated Linux machine that can be parked and woken with its memory intact, forked into copies and snapshotted. Give each agent, task or user their own sandbox, and let them run whatever code they need without touching anything else.

Sandboxes live in a **workspace**: one Zerops service of the type **Box Workspace** (`zbox@1`) in your project. It is a managed service, like a database: there is nothing to deploy, no `zerops.yaml` and no pipeline. You pay for the workspace's resources like for any other Zerops service, and the sandboxes inside it cost nothing extra ([pricing](/zbox/pricing)).

New here? Start with [Getting started](/zbox/getting-started).

## How it fits together

```text
Zerops project
├── your services (runtimes, databases, ...)
└── Box Workspace service = one workspace (a VM)
    ├── HTTP API, web console, sandbox ingress
    ├── bases and templates
    └── sandboxes, each a Firecracker microVM
```

- The **workspace** is a single VM with the CPU, RAM and disk you give it. It runs the Zerops Box orchestrator, which serves the API and runs the sandboxes ([workspace as a Zerops service](/zbox/workspace-service)).
- You manage the workspace through its **HTTP API**, the **`zbox` CLI**, the **web console** or `zbox mcp` for AI agents ([managing and accessing the workspace](/zbox/access)).
- Because the workspace sits in your project's private network, sandboxes can reach your other services, such as a database, if you let them ([networking](/zbox/networking)).

## Concepts

| Concept | What it is |
|---|---|
| **Workspace** | One Box Workspace service: the VM that hosts your sandboxes, with one API and one API key. |
| **Sandbox** | A Firecracker microVM with its own kernel, memory, disk and network. You run commands in it, open its ports and SSH into it. |
| **Base** | The image a sandbox boots from, pulled from a container registry or built from a Dockerfile on the workspace ([images](/zbox/images)). |
| **Template** | A base with a size and a policy. A **warm** template keeps a booted memory snapshot, so sandboxes made from it resume instead of booting ([templates](/zbox/images#templates)). |
| **Park and wake** | Parking stops a sandbox and frees its CPU and memory. Waking resumes it, by default from its memory image ([lifecycle](/zbox/lifecycle#park-and-wake)). |
| **Fork** | Copies of a sandbox that continue from its current state, running processes included ([fork](/zbox/lifecycle#fork-a-sandbox)). |
| **Snapshot** | A saved disk, optionally with memory, that you restore into a new sandbox ([snapshots](/zbox/lifecycle#snapshots-and-restore)). |
| **Lineage** | A sandbox together with everything forked or restored from it ([lineages](/zbox/lineages)). |
| **Policy** | The rules of a sandbox: its ports and who may open them, its egress, its secrets. The workspace and template policies set the limits ([workspace policy](/zbox/workspace-settings#workspace-policy)). |
| **Integration** | An API the credentials proxy calls on a sandbox's behalf, adding a credential the sandbox never sees. **Connectors** are ready-made integrations for Claude Code, GitHub and Codex ([secrets](/zbox/secrets), [connectors](/zbox/connectors)). |
| **Operation** | A long-running request, such as a create or a park, that you can wait for ([operations](/zbox/access#operations)). |
| **Event** | A record of something that happened to a sandbox, readable live or delivered by webhooks ([events and webhooks](/zbox/monitoring)). |
